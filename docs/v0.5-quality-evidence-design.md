# v0.5 Quality / Defect Evidence — Architect handoff

Design only for FR504/506–510/512–513. Separate normalized defect collection and pure analysis; existing v0.4 verification observations remain their own exact-version/target evidence, never merged into a defect or success score. Shared identities/windows/capability/conflict/completeness/quantile rules are normative in [delivery design](v0.5-delivery-flow-design.md).

## Defect collection and lifecycle

`quality-evidence-1`: approved system/project/provider scopes, collection/retrieval boundary, independent configured Bug-type population, state/field policy fingerprints, field/history/window capabilities, records, explicit mappings and fixed diagnostics. Bug reference reuses the exact scoped WORK_ITEM identity of existing evidence when one exists, with a declared DEFECT role; it never creates a parallel inferred work item from an alias string.

Allowlist: reference, immutable source observation/revision alias, observed_at, explicit type/state/category, state_as_of, created_at, explicitly observed completion/reopen transitions or configured resolution pair, nullable approved priority/severity category, field-definition/mapping fingerprint and explicit references to approved requirement/work-item/component membership. No descriptions/title/comments/person/area-path contents/logs/native provider URLs. Priority and severity are separate categorical provider assertions, not ECL finding severity. Unknown configured values enter an UNKNOWN bucket with exclusion reason, never default critical/low.

Project config explicitly selects native Bug work-item type(s), completion/open/removed states and optional priority/severity reference fields + approved category maps. No universal Resolved/Closed label assumption: process states differ, and source-owned field policy declares which state/time represents the selected completion endpoint. Microsoft [workflow categories](https://learn.microsoft.com/en-us/azure/devops/boards/work-items/workflow-and-state-categories?view=azure-devops) describes process-dependent state categories; [work-item field definitions](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-item-types-field/list?view=azure-devops-rest-7.1) supplies schema metadata. These are read-contract candidates; availability/semantics still need project/profile validation. Optional severity absent from a process is UNSUPPORTED, not zero severity.

Lifecycle: created event → explicit OPEN/COMPLETE/REMOVED state transitions. Reopened = an explicit transition from configured COMPLETE to OPEN, with known adjacent states and source event sequence, inside window. A currently OPEN bug with an old resolved field is not proof of reopening. Truncated history cannot prove no reopens; observed explicit reopen positives survive as PARTIAL counts. Conflict quarantine prevents contradictory copies from becoming a resolved favorable case. Removed/deleted items are separately excluded, never silently resolved; visibility/deletion gaps taint enumeration completeness.

An item may complete/reopen/complete multiple times. Event counts and distinct bug counts are different dimensions: report resolved-bug throughput and reopened-bug count as distinct identities per window; expose optional supporting completion/reopen event counts separately, never substitute them into bug denominators. For per-bug resolution durations select last qualified completed episode in window using delivery episode policy with selected start=creation for first lifecycle episode, or explicit COMPLETE→OPEN reopen event for later episode. Completion must follow that start; missing history/episode start yields unavailable duration, not assumed lifetime/resolution0. First-response time, escaped-defect rate and defect density are out of scope.

## Quality metrics

| Metric | Population / definition |
| --- | --- |
| Bugs opened | Distinct independently selected Bug identities with explicit created_at in half-open window; creation field does not mean reopen. Missing creation/failed type enumeration prevents complete total. |
| Bugs resolved | Distinct selected Bugs with explicit configured completion entry in window, regardless of later reopen; current-state snapshots/last resolved date do not replace historical event enumeration. |
| Open bugs | Independent Bug inventory immediately before window.end classified OPEN under exact snapshot/history qualification; currently retrieved state is not historical inventory. |
| Open age | `(window.end−created_at)/86400`, distinct known-age open Bugs; missing dates remain separate unknowns; use same buckets and configurable>=30days aged threshold. |
| Resolution median/p75/p90 | One qualified representative completed episode per distinct Bug/window; shared exact duration/nearest-rank/minimum-n policy and open-work censoring disclosure. |
| Aged bugs | Distinct open Bugs with known age>=threshold; known counts plus unknown-age counts, no inference that unknowns are young. |
| Reopened bugs | Distinct Bugs with explicit COMPLETE→OPEN event in window; history unsupported/unknown/failed makes value null unless retained positive PARTIAL evidence is explicitly labelled observed subset. |
| Priority / severity | Independent selected Bug inventory at window.end by configured approved category; raw count per category, UNKNOWN/unavailable count and known/selected denominator. No field→dimension unavailable; no inferred category/order from text. |
| Opened vs resolved | Two event populations in the same window, report observed counts and difference only when comparable complete selection is qualified. A resolved Bug may have been created before window; this difference is not a conservation equation for backlog because reopen/removal exist. |

Metric availability/count/eligible/excluded/status axes match Delivery. Complete supported empty Bug inventory yields measured open/aged/opened/resolved0 when requisite event/field enumeration is also complete, while age/resolution quantiles and category proportions with zero denominator are null EMPTY_POPULATION. Unsupported reopen/severity remains UNAVAILABLE even when Bug count is0. Complete inventory does not certify complete event history. Partial selection retains observed positives but suppresses trend and inflow findings requiring totals.

Current/previous trends use identical Bug-type/state/episode/category/mapping policies and equal windows; count absolute deltas are observations, not quality rankings. Qualified execution outcomes are imported unchanged from v4 and display original target/version/source times, missing selected-test observations and qualification reasons. A FAIL is not a Bug unless an explicit accepted relationship says so, and a resolved Bug does not prove passing tests. No simplistic failure rate, defect-density, severity-weighted or quality score.

## Component / requirement mapping

Reuse exact explicitly declared v4 REQUIREMENT_WORK_ITEM or validated v3 WI implementation paths, with identity/provider/project/repository/configuration/snapshot joins. A Bug with a qualified WI→component path may appear on all explicitly reached components; retain every support hop/status/source boundary. Requirement context is only the explicit requirement→same WI path, not title/type similarity. No new BUG_REQUIREMENT/BUG_COMPONENT inference grammar is introduced. A source-owned exact membership assertion is allowed only under the separately typed component-mapping contract in the composition design; mapping fingerprint and per-item lookup completeness must accompany it.

Unmapped Bugs remain in global populations with mapping-unavailable reason; they cannot become component0. Unknown target components remain unresolved, not manufactured. Distinct Bugs count once in each supported component and once globally, never sum overlapping component counts into a total. Negative component totals require complete population AND complete eligible mapping lookup; a partial map only supports observed mapped positives. Titles, descriptions, area/iteration paths, names, pipeline labels and temporal proximity establish no membership.
